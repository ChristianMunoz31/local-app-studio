# Design guide

A short style guide for the app's UI, taken from the code as it is. Read it before you add or change a screen. The bar is "I downloaded the app, I opened it, and it just worked" (see [PRODUCT.md](PRODUCT.md)): a new screen has friendly empty states, no setup wall and an error that says what to do next. The app is calm, warm and glassy; keep to the tokens and components below rather than adding a second visual language.

Where a rule is enforced, the check is named.

## Tokens

Everything is in `src/index.css` (CSS variables) and `tailwind.config.cjs` (names). Never hard-code a color in a component; use a token so both themes work. The dark theme is `:root`, the light theme is `:root.light` (class on `<html>`; `darkMode: 'class'`).

### Surface and text scale (`--slate-*`, class `slate-slateNNN`)

The scale is semantic and flips with the theme, so the same class reads well in both. Low numbers are strong text, high numbers are surfaces. Do not use Tailwind's own `gray`, `slate` or `zinc` classes.

| Token | Dark | Light | Use |
| --- | --- | --- | --- |
| `slate100` | 236 228 214 | 31 41 55 | Headings, body text on cards (11.8:1 dark, 14.4:1 light) |
| `slate300` | 214 203 186 | 75 85 99 | Secondary buttons, labels (9.3:1, 7.4:1) |
| `slate400` | 171 158 140 | 90 98 112 | Captions, helper text, placeholders (5.7:1, 6.0:1) |
| `slate500` | 168 155 138 | 107 114 128 | Quietest allowed text, icons (5.5:1, 4.7:1) |
| `slate600` to `slate800` | warm darks | near whites | Fills and dividers, never text |

Ratios are the token over the default glass card. The plain look's light page is a flat pearly white (`PEARL_PAGE`, `rgb(251, 249, 246)`), a little below white, so text sitting straight on it reads about 5 percent lower (`slate500` 4.6:1, `slate400` 5.8:1); the theme tests check those pairs. The worst case (the strongest background preset under a card) is what the comments in `index.css` and the tests use. Do not go quieter than `slate500` for text.

### Accent text (`text-accent-<name>`, `--acc-*`)

Colored TEXT uses the adaptive accent tokens: pale in dark, saturated in light. Decorative fills keep the fixed `*Light1` color classes (`red-redLight1`). Names: green, red, yellow, orange, cyan, purple, teal, blue, fuchsia, amber, indigo.

| Token | Dark | Light | Meaning |
| --- | --- | --- | --- |
| `accent-green` | 154 224 149 | 4 108 78 | OK, running, saved (9.5:1, 6.3:1) |
| `accent-red` | 255 166 193 | 185 28 28 | Error, destructive (8.1:1, 6.3:1) |
| `accent-amber` | 251 191 36 | 180 83 9 | Warning, needs a look (8.9:1, 4.9:1) |
| `accent-indigo` | 165 180 252 | 67 56 202 | Links, Assistant, focus (7.4:1, 7.8:1) |

Every text color must reach 4.5:1 (WCAG AA, normal text) on its real background, in both themes, including the strongest background preset. A status chip is the accent text on a 15 percent tint of itself, which is the harder case, so it has its own test: `src/utils/__tests__/pillContrast.test.js` computes the chip ratio from `index.css` for the worst light and dark backdrops. Change an `--acc-*` value and that test tells you if a chip stopped passing. Non-text parts (input borders, focus ring) need 3:1; the comments next to `--glass-input-border` and `--focus-ring` record the ratios. Never rely on color alone: pair it with words or an icon.

### Surfaces (glass)

`glass` (cards), `glass-dense`, `glass-strong`, `glass-flat` (inside a blurred overlay), `glass-subtle` (a tile inside a card), `glass-input` (fields), `glass-overlay` (modal scrim) and the assistant panel variants. They are token backgrounds with a 1px token border and a soft shadow; radius is added by the component. Never nest one blurred class in another blurred element; inner tiles use `glass-subtle` or `glass-input`.

### Focus

Every control has a visible focus ring: `focus-visible:ring-2` with the slate-blue ring for buttons, `--focus-ring` (indigo, 5.7:1 or better) for inputs and links. Never remove an outline without a replacement.

### Spacing, radius, type

- Spacing is Tailwind's default 4px scale, no custom values. Cards use `p-5`; a card body stacks with `space-y-3` or `space-y-5`; a page is a column of `SectionCard`s with `space-y-5`.
- Radius: `rounded-md` (0.375rem) for buttons and inputs, `rounded-2xl` for cards and dialogs, `rounded-full` for chips. The config overrides `sm`, `md` and `lg`, so check `tailwind.config.cjs` before you use them.
- Parts of the catalog (`packages/runtime/src/catalog/parts/`) and the kit styles they import use theme variables only, through the classes in this guide (`slate-slateNNN`, `accent-*`, `slate-brand*`, `glass*`, `rounded-*`) or `var(--name)` from the theme contract. No `#hex`, `rgb(`, palette name (`red-red`, `gray-`), `white` or `black` in a part, so every app theme can restyle it. `src/catalog/__tests__/themeAudit.test.ts` fails on a fixed color that is not on its allowlist; the one entry is `text-white` on the primary button. The Studio screens use tokens too: `src/studio/__tests__/themeAudit.test.ts` reads every `.ts`, `.tsx` and `.jsx` file under `src/studio` outside `__tests__`, strips comments, and fails on a `#hex` or `rgb(` color inside a string, on a palette, `white` or `black` color class (`red-red` is `accent-red`; `slate-slateNNN`, `slate-brand*` and `accent-*` are the tokens), and on `text-white` in a string that does not also hold `bg-slate-brand` (white text only sits on the brand fill, which the theme engine keeps at 4.5:1 or better). Its allowlist is empty. See [THEMES.md](THEMES.md).
- Type is Inter with a compact scale (the config overrides Tailwind's sizes): `xs` 9px, `sm` 11px, `base` 13px, `lg` 15px, `xl` 17px, `2xl` 21px, `3xl` 23px, `4xl` 27px. Body text is `text-sm`; helper text `text-xs`; card titles `text-sm font-bold tracking-tight`; small caps labels `text-[10px] uppercase tracking-widest`. Weights are 400, 500, 600 and 700. Numbers that line up use `tabular-nums`. Do not put body text in `text-xs` over a busy background.
- Touch targets: icon buttons are `w-9 h-9` on narrow screens and `sm:w-7 sm:h-7` on wide ones. Keep that.

### Layout parts: Columns, Column, Row

- **Columns** is a CSS grid of 2 to 4 `Column` parts. `layout` (`equal`, `wide-left`, `wide-right`, `sidebar-left`, `sidebar-right`) and the column count pick a literal class from a table in `packages/runtime/src/catalog/parts/Columns.tsx` (`grid-cols-1 md:grid-cols-[2fr_1fr]` and so on), so below `md` (768 px) every column stacks. `wide` is `2fr` against `1fr`; `sidebar` is `minmax(12rem,1fr)` for the outer column against `3fr` for the rest. `gap` is `gap-2|4|6` (`calc(var(--spacing) * n)`, so the theme density applies) and `align` is `items-start|center|stretch`. No colors. A fifth column (not valid) wraps the four-column template; fewer than two is one column.
- **Row** is `flex items-center` with `gap`, `justify` (`justify-start|between|end`) and `wrap` (`flex-wrap|flex-nowrap`). It holds small parts in one line; its allowed children are the list `ROW_CHILDREN` in `Row.def.ts`.
- Class tables live in `packages/runtime/src/catalog/parts/layoutClasses.ts` (`GAP_CLASS`, `pickClass`). A stored value that is not a key of a table falls back to the default (own keys only), and the JS defaults equal the zod defaults.
- On the Design canvas each Column is its own drop zone, side by side (`CanvasNode` gives no between or after zones under Columns, like Tabs); an empty Column shows the fill zone. Blocks are named `Column 1 of 3`. The parts of a Row get inline zones (`DropZone orientation="inline"`, a thin vertical bar). A Column is not dragged: Move up and Move down reorder columns, and Move to... lists the columns by name for parts.
- Child counts (`PartDefinition.childCount`) are enforced by `layoutTree.ts` (`insertLayer`, `moveLayer`, `removeLayer` refuse with `child_count`; `dropTargets` leaves such places out). `addColumn` adds a Column with one text. Settings: Columns has `Add a column` (off at 4), a Column has `Remove this column` (off at 2) with the same Undo as Delete.
- **Choice settings** are Studio only: `src/studio/lib/choiceProps.ts` lists the enum and number props a person may change, with plain labels, and `configureLayer` accepts those keys (`props.<name>`) checked against the part's zod shape. They are never feature slots.

### Parts side by side (widths)

- A layer may carry a `sizing` block beside `props`: `width` (`full`, `three-quarters`, `two-thirds`, `half`, `third`, `quarter`, `fit`) and `grow`. Absent means the whole row. Only parents that stack their parts lay widths out (`SIZED_PARENTS`: Page, Section, Card, Collapsible, Column, Tab); a Page, Tab or Column never has one (`UNSIZED_TYPES`). Under Grid, Row, Tabs, Columns and a page header a stored width is kept and ignored, and Design hides Width there.
- Runs of consecutive parts that are not the whole row are one wrapping flex row (`ROW_CLASS`, `gap-4`, one column below `md`). Item classes come from `WIDTH_CLASS` (`basis = f * 100% - g * (1 - f)`, so widths that add up to one row fit one line at any density). The class table and the grouping helper `sizingSegments` live in `packages/runtime/src/catalog/parts/sizingClasses.ts` and are shared by `SpecRenderer` and the Design canvas (`canvasChildren` in `DesignCanvas.tsx`), so the canvas and the Preview draw the same row. With nothing side by side the DOM is exactly the one without rows.
- **Drop beside.** While a part is dragged, every block in a stacking parent shows a thin "Drop beside" bar at its left and right side (`SideZone`, `data-zone="side:<id>:left|right"`, offered by `sideTargets` with the same holding and count rules as the places between parts). Dropping on a whole-row block makes both halves; dropping beside a sized block gives the new part that block's width and leaves the block as it is. The row wraps when it must. Moves never change widths: a part moved out of a row keeps its own width and its old neighbour keeps its width (the settings line tells the person, so they can set it back).
- **The handle.** Between two neighbours on one line (greedy packing in twelfths: quarter 3, third 4, half 6, two-thirds 8, three-quarters 9, fit 0), both share widths and neither growing, the left block carries a focusable separator (`ResizeHandle.tsx`, `aria-label="Resize <left> and <right>"`). ArrowLeft and ArrowRight step it; a pointer drag previews the widths on the canvas and changes the tree once, on release. Positions of a pair that fills the row (a step right widens the left one):

| Position | Left | Right |
| ---: | --- | --- |
| 0 | quarter | three-quarters |
| 1 | third | two-thirds |
| 2 | half | half |
| 3 | two-thirds | third |
| 4 | three-quarters | quarter |

  Any other pair (third plus third beside a third) steps on the ladder quarter, third, half, two-thirds, three-quarters: left one rung up, right one rung down, never off the ladder. At the last position the handle says "The handle cannot go further this way."
- **Width setting.** Settings ends with Width, after the part's own words and choices (the popover is content first, then Width, then the note "Apply changes the page. Save keeps it."). Width offers (widest first: Whole row, Three quarters, Two thirds, Half, A third, A quarter, Only what it needs), Grow to fill (off at Whole row, "Fills any room left in the row.") and a plain line such as "Takes half the row". A change applies at once. Whole row deletes the block, so half and back gives the original bytes.
- **Shrink and Widen** are block toolbar buttons (after Move down), shown where Width is. The pair's handle moves first; with no pair, or at its end, the part steps alone on fit, quarter, third, half, two-thirds, three-quarters, whole row, keeping Grow except at the whole row. There is no Alt+Arrow shortcut for widths (Alt+ArrowLeft is browser Back); on a part placed freely on a grid the Alt+Arrow keys are handled and never go Back.
- **Undo.** Every width change, side drop and resize (one drag is one step) is one history entry and says what changed in the status line with Undo, like Delete. The pure helpers are in `src/studio/lib/layoutTree.ts` (`sideTargets`, `besideSizing`, `insertBeside`, `moveBeside`, `setSizing`, `resizeHandles`, `pairCandidates`, `resizePair`, `stepWidth`); `replaceLayer` keeps the replaced layer's width (a feature update, Detach and Save as feature keep the place). The words are in `src/studio/lib/sizingWords.ts`.

### Parts placed freely on a grid

A Grid with **Place parts freely** turned on lays its parts on 12 columns from `md` up (one column below `md`, in reading order). Each part has a place: a column, a width in columns, a row and a height in rows. Words are in `src/studio/lib/gridWords.ts`; the pure editing is in `src/studio/lib/gridLayout.ts` (`syncGrids` keeps the invariants after every edit). Nothing here animates, so `prefers-reduced-motion` needs no rule, and the DOM order is the reading order (row, then column).

- **The switch.** Grid settings have a switch **Place parts freely** with the hint "Put each part at a column and row of its own, on 12 columns." Turning it on says "Auto grid now places parts freely." and gives each part the next free cell, `12 / columns` wide, in its old order. Turning it off, when a part has a place, asks "Stop placing parts freely?" with "Their places are forgotten. The parts stay, one after the other. Ctrl+Z brings them back." The buttons are **Keep places** (it has the focus when the question opens) and **Stop placing freely**. The settings stay open, and the focus returns to the switch on either button. Off says "Auto grid now puts parts one after the other." With no placed part it asks nothing.
- **Drop.** While a part is dragged, a free Grid that accepts it shows the 12 columns and the rows (plus one more row) as dotted cells, each with two dotted layers so the line holds against every theme. The cells the part would take are outlined with a solid line and a pill: **Drop here** when they are free, **Cells taken** (red, with a stop icon) when they are not. The two differ by line style and words, not by color alone. A new part is 3 columns wide and 1 row high; a part moved inside its own Grid keeps its size. A part from the menu bar cannot be dropped on a cell by pointer; **Move to...** puts it at the next free cell. A drop on taken cells is refused with the words of the validator: "Two parts cannot share the same cells. Move or resize one of them to empty cells."
- **Spoken while dragging.** Drags are pointer only. The cell is spoken once on entry ("Text is at Auto grid, column 4, row 2.") and once on the drop ("Dropped Text at Auto grid, column 4, row 2."); cells in between are shown, not spoken. A taken target says "Text is not over a place." and a drop there "Text was not dropped."
- **Move.** Drag the block by its handle onto a cell, press Alt+Arrow on the focused block (one cell per press), or use the Place section. A placed block has no **Move up** or **Move down** (the order follows the place). A move says "Moved to column 4, row 2." A move that changes the reading order re-sorts the page, so Studio puts the focus back on the block and does not speak the move live: the block's description says its place ("column 4, row 2, 3 columns wide, 1 row high"). Every other move and every resize is spoken once, a quarter of a second after the last key, so a held key speaks only the final place.
- **Resize.** A selected placed block has two handles, a width handle on its right edge and a height handle on its bottom edge (separators, 24 px wide, named "Change the width of <part>" and "Change the height of <part>"). They are in the tab order only while the block is selected. Drag them to a cell, or press Arrow keys (one cell), Home (the smallest) or End (as large as the free room allows). Value text reads "6 columns wide, columns 4 to 9" and "2 rows high, rows 3 to 4". Alt+Shift+Arrow on the block does the same (left narrower, right wider, up shorter, down taller; the left and top edges stay). A change says "Now 6 columns wide, columns 4 to 9." or "Now 2 rows high, rows 3 to 4."; one drag is one Undo step.
- **Alt+Arrow and Back.** The Alt+Arrow handler always calls `preventDefault`, also at an edge, on a refusal and on a held key, so Alt+ArrowLeft never goes Back; an e2e step proves the URL and history do not change. The leave guard of the workspace stays as the safety net. In the installed desktop app (WebView2) this is a manual check. Alt+Shift can switch the Windows input language when several keyboard layouts are installed; the Place section does the same without Alt.
- **Place section.** Settings of a placed part have **Place**: boxes **Column**, **Width in columns**, **Row** and **Height in rows** (each in a `data-setting-target="place.<field>"` wrapper), and **Fill the row** (12 columns wide from column 1, in the rows it is in). Typing changes only the draft; Enter or leaving the box applies it; ArrowUp, ArrowDown and the spinner apply at once. A value that is not a whole number says "Use a whole number from 1 to 9."; a value out of range explains the limit ("Column can be 1 to 9 while the width is 4 columns."); an overlap says "Cannot place it there: <part> is in column 5, row 2." The problem line is a `role="alert"`, and the failed box has `aria-invalid="true"` and `aria-describedby` to it. A refused blur puts the stored value back; a refused Enter keeps what was typed. **Move to...** on a placed part lists **Choose column and row...** first; it opens the settings with the focus on Column.
- **Refusals name the blocker and the limit.** "Cannot move right: Heading is in column 5.", "Cannot make it taller: Notes is in row 4.", "Column 1 is the first column.", "Column 12 is the last column.", "Row 1 is the first row.", "Row 60 is the last row.", "It is already 1 column wide.", "It is already 1 row high.", "A part can be at most 12 rows high." Keyboard, handle and Place refusals are spoken at once through a `role="alert"` line (the same words again are spoken again).
- **Narrow screens.** Below `md` the canvas shows one column, but keys, handles and Place still change the stored place, and their words end with "The grid shows one column on a narrow screen."
- **Other words.** "There is no free room left on this grid.", "This part is not on a grid that places parts freely.", "That place does not fit on the grid.", "This grid holds too many parts to place them freely." Help lists the keys (Alt+Arrow on a placed part, Alt+Shift+Arrow, Arrow keys and Home or End on the handles).

### Review place words (phase 22)

When the helper places parts on a free grid, the review pane says where, in plain words, from the before and after designs it already holds (nothing new travels from the server). Parts are matched by id. The sentences are in `diffSpecs` (`src/studio/lib/specDiff.ts`, using `gridWords.ts`), the past tense lines in `placeBullets` (`promptBullets.ts`) and the list is `PlaceLines` (`PromptBullets.tsx`), a list named "Places" right after the ask result.

- **Sentences (Show every change).** A new page with a free grid: "Places 6 parts in a grid on Home." A grid turned on or off: "Turns on Place parts freely for Auto grid on Home." A part moved: "Moves Chart to the top row." (row 1 is "the top row", else "row 3"; only the column: "column 7"; both: "column 7 of row 2"). Several parts of one name moved to one place are one line: "Moves Number tiles to the top row." A part resized: "Makes Chart 8 columns wide." or "Makes Chart 6 columns wide and 2 rows high." Moved and resized: "Moves Chart to column 7 of row 2, 6 columns wide." A part put on the grid: "Places Number tile at column 1, row 5, 3 columns wide." (the height only above one row). More than 6 on a page: "Changes the place of 3 more parts on Home."
- **Bullets (Places list).** The same lines in the past tense without a full stop ("Moved Chart to the top row", "Placed Number tile at column 1, row 5, 3 columns wide", "Turned off Place parts freely for Auto grid on Home"), the first four, then "and 2 more parts moved or placed" (it counts parts; "and 1 more part moved or placed" for one). When a page changed around a free grid and no part on it moved or was resized, the last line is "Nothing moved on the grid". The list is absent when no place changed.
- **Ask words.** `placeAsk` (`askOutcome.ts`) reads each clause: stacking words ("one column", "no grid", "one after the other", and "stack" or "flow" only as the clause's verb, as in "Stack these" or "make it flow", never "cash flow" or "the Stack table") turn the grid off; "grid", "freely" and "as a dashboard" turn it on; "move", "put", "place", "resize", "wider" and the like move or resize, and a position word ("top", "bottom", "left", "right", "beside", "under", "above", "below") counts only beside one of those. A clause whose verb is remove, delete, rename, hide or show is never a place clause. Flow beats free beats move; "do not stack" and "never move" are not place asks; "add a tile" is an add, not a move; "one column wide" is a resize. A place clause is Done only by a place change of its own kind (a move names its part by its part word or label); a clause with an ordinary verb that a place word misled is also Done by its ordinary change, and a Done place clause also explains "Changes the layout of Home", so that line does not show under "It also changed". Place changes never show under "It also changed". A clause that names the menu, or a table, field, column, page or screen with no part word ("Move Orders to the menu", "Move the Notes field to the top"), is not a move and asks for no relayout. "and" or a comma before put, or before move, place, swap, resize, stack or flow followed by a determiner or pronoun ("the", "a", "it", "them", "all" and the like), starts a new clause; "Add Name, Stack and Status fields" is one clause (a list of names), and a bare flow word right before table, field, column, page or screen, or in a clause that names one of them and no part word, is a name, never a flow ask. A part word right before table, field, column, page or screen is part of a name ("Move the Phone number field", "Move the Total column" are no grid moves), in the move check and in the parts a clause names alike. "Add a search box to the menu" is no layout change. "Stop stacking the parts" is negated, not a flow ask. Known limits: "Make the tiles stack" and "Let the parts flow" are missed (the flow word is not the clause's verb; the safe direction, nothing is relaid out). "Show the chart below the tiles" (show plus a position word) is not a move; it is judged Not done with the Design exit.

### The menu bar on the canvas

- **Where it is.** While the menu bar is on (Look, Menu bar), the canvas draws it in the app's look: above the page across the top, or beside it down the side (`MenuCanvas.tsx`, inside the same theme scope as the page). Its two sides are boxes, `start` and `end` (`data-menu-slot`, named "Menu bar, left" and "Menu bar, right" for the bar across the top, "Menu bar, top" and "Menu bar, bottom" for the bar down the side, by `menuSideName` in `designLabels.ts`); the page links between them are an inert picture drawn with the runtime's own classes (`menuClasses.ts`). The Look tab (`MenuPicker.tsx`, above the themes) keeps the bar on or off, its position and style, and offers "Add a button to the menu bar" (a new Button at the right or bottom end, with Undo) and "Show the parts", which switches to the Features tab where Add here on the bar puts other parts.
- **What fits.** A slot holds Button, Link, Search box, Quick add, Text and Row (`MENU_PARTS`, `packages/runtime/src/spec/menuSlots.ts`); a Row on the bar holds the same without a Row. At most 6 parts in a slot and 24 on the bar. An empty slot says "Fits here: Button, Link, Search box, Quick add, Text, Row". While a part the bar does not take is dragged, the slot shows that line in a dashed box (a droppable `{ kind: 'refuse' }`); a drop there answers in the status line with the validator's own words, "The menu bar can only hold: Button, Link, SearchBox, QuickAdd, Text and Row.", or "Saved features cannot go on the menu bar." for a feature. The shelf marks the six parts with "Fits the menu" (`fitsMenu`, in the tile footer).
- **One tree per place.** The menu is edited as a tree: `AppMenu` over two `MenuSlot` layers with the ids `@menu`, `@menu-start` and `@menu-end` (`src/studio/lib/menuTree.ts`; `@` is outside `LAYER_ID_RE`, so they never meet a part id). `layoutTree.ts` treats a menu tree like any other: `canHold(parent, type, root)` reads a slot as the menu's part list, `locked` keeps the bar and both slots from moving or being removed, and a slot counts 0 to 6 children. `composeMenu(look, tree)` writes the slots back as `menu.start` and `menu.end` (an empty slot has no key; no look means no menu). The look (position and style) stays in the session as before.
- **Two scopes, one history.** `useLayoutEditor` holds both trees and one undo history; a result changes one tree (`apply(result, tree)`) or both (`applyPair`, a part moved between the page and the bar is one step). `DesignContextValue` has `tree` and `menu`: the page scope's `menu` member is the bar's scope (its `root`, `ctx` from `menuPartContext(spec)`, its own `zones`, `remove` and `move`), which `MenuCanvas` provides to the blocks in the bar. So `CanvasBlock`, `DropZone` and `BlockSettings` work there unchanged: Settings, Move up and Move down, Alt+ArrowUp and Alt+ArrowDown, Delete, Undo and Redo. Draggable ids in the bar are `menu-block:<id>` with data `{ kind: 'block', id, tree }`; drop zones carry `tree`, and their zone keys are `@menu-start:0`, `@menu-end:2`.
- **Between the page and the bar.** Dropping a block of one tree in a place of the other, or choosing Move to... (which lists "Menu bar, left, place 1" beside the page's places), runs `transferLayer`: the part is adapted (`adaptForPlace`: a Search box keeps only its hint text on the bar, and gets the page's first list and its text fields going back, or is refused when the page has none), checked with the other place's rules (`checkLayer(..., place)` must add no issue the part did not have), taken out of one tree and put into the other with fresh ids for any id taken there, and kept at its width. The status line says "Moved Button to the menu bar." or "Moved Search box to the page." with Undo.
- **New parts on the bar** come from `newMenuLayer`: a Button opens a form to add a record in the first table (labelled "Add to <Table>", for example "Add to Crews"; with no table it goes to the first page and says "Go"), a Search box has no source (the runtime gives it the open page's first list; on the canvas a page with no list shows "Hidden on this page: it has no list."), a Row starts empty, the rest are built like on a page. The status line says "Added Button to the menu bar." with Undo.
- **What it does.** A Button's Settings starts with a select, **What it does** (`ActionSettings.tsx`): "Goes to a page" or "Opens a form to add a record". It applies at once like Width and says so in the status line with Undo (`setButtonAction`, `src/studio/lib/actionKind.ts`: the first page that opens without a record, or the first table in create mode; with no table, "This app has no table yet. Put a part that shows records on a page and press New table on it."). It shows on the page and on the bar, but not for a button that deletes the record or opens a form that edits. In the bar, a Search box's settings are its hint text and the line "Searches the first list on the page that is open. On a page with no list it is hidden."
- **Page header and page links** are drop zones on the canvas like any container: a page header takes up to three buttons, links and quick adds, page links up to three buttons and links (`notAllowedMessage` has their words).
- **Save.** `composeMenu(menu, menuRoot)` is written with the page; the bar counts as changed when it differs from what was loaded. Turning the bar off in Look keeps the parts in the session (turning it back on before Save brings them back) and the hint says "Saving with no menu bar removes the 2 parts on it."; Save then writes no `menu` key.

### Data connections on the canvas

- **Bind on drop.** A built-in data part dropped on a page (or added with Add here) goes through `planDrop` (`src/studio/lib/bindOnDrop.ts`, choices in `bindChoice.ts`), not through `newPartLayer` alone. In order: a list of the page that fits the part (declared fields before `created_at` and `updated_at`, so a Timeline lands on a real date); else, when exactly one table of the app fits, a new page source on it, made as part of the same history step (Undo takes the part and the list away together; the status line says "Added a list of Crews to this page." or, for a record part, "This page now shows one Crews record from its address."); else, when several tables fit, the part is placed **not connected** and its settings open on the List (or Table) setting with "Pick a table for the new Table of records."; else the part is placed not connected with an offer (`offerFor`): New table, and Add a field when a table can take the field. Quick add and Form prefer the tables the page shows, and a Form on a record page edits that record. Quick add only takes a table it can save with one text field (`quickAddFits`). Words that name the table replace the sample app's ("Add to Crews", "Crews by Status"), and a number tile on a table with no number field counts rows.
- **Sources are part of the session.** `useLayoutEditor` also holds the page's draft `sources` in each history entry (`apply(result, tree, sources)`), so Undo and Redo restore them with the layout. `DesignSession` builds `draftSpec` and `draftCtx` from them (`withPageSources`), save writes `{ layout, sources }` for the page, and the session is dirty when either changed. The draft `tables` are part of the session too: New table and Add a field are one history step each, `draftSpec` uses the draft tables, and save writes them. A save that removes table data asks "Save and remove data?" like the Data step (one shared helper, `dataRemovals`); when the question cannot be answered the save refuses with "These changes remove data, so they need your OK first."
- **The indicator.** Every built-in data part and every saved feature block that uses a table shows one pill, in one of three states (a fourth, "Uses slot", only in the Feature builder). It is computed by one pure function, `partIndicator` in `src/studio/design/indicator.ts` (`specNeeds` lists the parts of a whole app that need something, `entryNeedsTable` answers for a shelf or Features tile), and drawn by one component, `ConnectionBadge.tsx` (`data-indicator=<state>`, and `data-connection-badge=<table>` on the connected and slot pills). The states: **Connected to <Table>** (green), **Needs a table** (amber), **Needs <a kind field>** such as "Needs a yes or no field" (amber, the part's table exists but no table has the field it needs), and in the builder **Uses slot <Label>** (neutral). A part that uses no data (Heading, Text, Button, Row), a menu search box and the parts inside a feature block get none. The pill sits in the flow of the block, in its first row, so it never covers another part's pill or words; a feature block's pill is above the block. On the canvas a connected or slot pill is the **Change table** button (no title, because its name already says it: the visible text plus a screen-reader-only ". Change table", so the name holds the visible words (WCAG 2.5.3); no aria-label): it selects the part (a feature block: the block) and opens its settings on the List or Table setting. A feature block that needs a table has the same kind of button on its needs pill (name "<words>. Open settings"), which opens its settings. The needs pill of a data part is inside its dashed box (below), and the popover's pill is plain text. The settings popover starts with the pill, then one line for what the part does with the table: "It shows records.", "It shows one record.", "It adds records." or "It edits this record."; a part that needs a table says "Pick one below." (or its offer sentence).
- **Needs a table or a field.** A part with no table yet is not drawn; the canvas shows a dashed box `data-not-connected` whose first child is the pill ("Needs a table" or "Needs a yes or no field"), then, when a table fits, a **Connect** button (`aria-label="Connect <Part> to a table"`) that selects the part and opens its settings on the List or Table setting. When no table fits (`offerFor`, `NotConnected.tsx`), the box shows the offer after the pill: "This app has no table yet." with **New table**, or, for a needed field, **Add a field** (only when a table can take one more field) and **New table**. They open `NewTableDialog.tsx` and `AddFieldDialog.tsx`; the settings popover has the same buttons. In the Feature builder the hint reads "This feature has no table slot yet." and the buttons **Add a table slot** and **Add a field slot** (aria "Add a table slot for <Part>", "Add a field slot for <Part>"). The List setting offers the page's lists and one "New list of <Table>" per table that fits (for a record part on a record page, "New: the <Table> record from the page address"); the Table setting of a Quick add lists only tables it can save. Apply builds the part again on the choice with `connectLayer` (it keeps its id and width) and adds the list in the same step. A part that needs a table cannot be saved: **Save** is disabled with "Connect the parts that need a table, or delete them, to save."
- **Data connections list.** Above the canvas, `ConnectionIssues.tsx` (`aria-label="Data connections"`) lists `connectionIssues` of the other pages and the write parts of the open page. A part of the open page that needs a table is not listed: its own dashed box with **Connect**, its settings popover and the Save reason already say it (at most three places say one fact). For another page: "The Table of records on Stats needs a table." or, when no table has the field, "The Checklist on Stats needs a yes or no field." (button **Open page**; it blocks Next, and Save on that page), and "The Quick add on Home adds to People, but nothing on this page shows People." ## Copy

- No em dashes or en dashes anywhere (UI, docs, PR text). `npm run check:em-dash` fails the build when user-facing JSX source (not comments or tests) contains one; keep docs and PR text clean as a writing rule. Use a period, a comma or a colon.
- Plain words, short sentences, second person ("Check that the data folder can be written to"). No jargon a mainstream user would not know: say "your data folder", not "the data directory"; say "computer", not "host".
- Sentence case for headings, buttons and labels: "Save as feature", not "Save As Feature". Proper names keep their capitals: Local App Studio, Assistant, Ollama.
- Describe the product in store pages, the website and release text as a desktop app with a built-in helper. Do not present it as a hosted model, a chatbot or a way to buy model access: some stores prohibit selling that. Inside the app the helper is called Assistant.
- Say what is true about privacy and cost plainly: "Your data stays on your computer."
- Do not blame the user, and do not show raw errors, stack traces, status codes or provider text. Errors come from fixed copy (`server/license/messages.js`, `src/utils/apiError.js`, `withheldMessage()`).

## Empty states

A list with nothing in it explains itself and offers the next step in one click. Pattern: one plain sentence in `text-sm text-slate-slate400`, then the same button the page uses to add one, labelled for the first time.

```jsx
// src/studio/pages/FeaturesPage.tsx
<div className="space-y-3">
  <p className="text-sm text-slate-slate400">No features yet. In Design, select a part and choose Save as feature.</p>
  <button type="button" className={btnSecondary} onClick={() => fileRef.current?.click()}>Import a feature</button>
</div>
```

An empty state also says when it will fill. A feature that needs an opt-in or Pro is not an error: show `NetworkOptInNotice` or `ProGateNotice` in the same place, never a blank card or a spinner that never ends. A fresh data folder must show these, never an error wall (the first-run Playwright project covers it).

Loading uses a skeleton, not a spinner with no text.

## Errors

Every error says what happened in plain words and exactly what to do next. Pattern: what happened (without blame), then the action, with the place to do it named like the menu path ("Settings > License").

Real examples from the code:

- `activation_limit_reached` (`server/license/messages.js`): "This key is already active on as many computers as it allows. On a computer you no longer use, open Settings > License and click Move to another computer, then try again here. If you can't reach that computer, email <support>."
- `activation_write_failed`: "Local App Studio couldn't save your license on this computer. Check that the data folder can be written to, then click Activate again."
- `cloud_disabled`: "Cloud AI was turned off, so nothing was sent. Try again to use the AI on this computer."
- `AI_BUSY_MESSAGE` (`src/utils/apiError.js`): "Assistant is busy with another request. Try again in a moment."

Rules: one next step is better than three; a retry that will not help is not offered; a field error uses `formErrorClass` and sits next to its field, with `aria-describedby` or `role="alert"`; a destructive action asks first through `ConfirmDialog` (`StudioConfirm` in Studio, see "Studio navigation"). Never leave the user at a dead end: a failure always keeps their data and says so when it matters ("Your data and everything in Local App Studio Free keep working.").

## Error codes

Every error the server sends, and every SSE `error` event, has one shape: `{ error, code, action, requestId, details? }`, plus `message` (a deprecated alias equal to `error`, kept for this phase) and any code-specific extras such as `issues`, `field` or `feature`. `error` is the plain sentence, `code` is the machine code (stable snake_case), `action` is the one next step, and `requestId` equals the `X-Request-Id` response header. The words live in `src/errors/copy.core.js` (rows a built app can send or show) and `src/errors/copy.studio.js` (Studio only, registered by `server/modules/studio.js`, so a built app's sidecar does not carry them). `server/errors.js` builds the envelope; the Studio translator is `src/studio/lib/errorWords.ts`. See [DEBUGGING.md](DEBUGGING.md) for the envelope in use.

A row either has its own sentence, or says `from <file>`: the sentence is then kept in that file (a registry such as `server/backup/errors.js` or `server/license/messages.js`, or the call site that throws it) and passed to `sendError` as `message`. The action is always in the copy file. The 186 rows below are one per entry of `ERROR_CODES`; `server/__tests__/designErrorRows.test.js` fails when a code has no row here. Codes marked client only (`network_unreachable`, `render_failed`, `chunk_load_failed`, the eight `feature_*` codes of the Feature builder and the two layout codes `grid_not_allowed` and `grid_overlap` and the three automation codes `auto_number_not_allowed`, `rule_field_missing` and `rule_not_allowed`; Design shows them as a refusal, and the server sends them only inside the `issues` of `invalid_spec`) are raised in the browser and never sent by the server. In the Studio rows at the end, a status of 0 in the copy file means the code travels as an SSE event or a build record, not as an HTTP status.

## Studio navigation

How a person moves through an app in Studio. The code is `src/studio/pages/AppWorkspace.tsx` (the shell), `components/StepHeader.tsx` (the rail), `lib/steps.ts` (the steps, pure) and `hooks/useStepChrome.ts` (what a step tells the shell).

- **Five steps, in the order of work.** Prompt, Design, Data, Preview, Build (`STEPS` in `lib/steps.ts`). The routes are `/apps/<id>/<step>`. The old `/review`, `/review/data` and `/review/design` redirect to `prompt`, `data` and `design`, and the old `/describe` redirects to `prompt` (search, hash and router state kept, history replaced). `/apps/<id>` lands on Prompt for a starter app (no tables and one page that holds only the starter heading, `isStarterSpec`), else on Design (`landingStep`). Prompt is where the words are written and where the helper's design is checked: the prompt is on the left and the review (`ReviewPane.tsx`) on the right from 1024 px, stacked below that (the route element is still `DescribeTab.tsx`). Design and Data are the two editors.
- **The rail.** `StepHeader` lists the five steps as links with a number, or a check mark when done, and `aria-current="step"` on the current one. Done comes from evidence, not from visits (`stepStates`): Prompt when a helper design was used for the app (`markHelperUsed` on Use this, remembered per app in browser storage by `lib/appMemory.ts`) and no design waits; Design when some page holds more than the starter heading (`hasDesignedPage`: a page with no lists and nothing but one Heading, or nothing at all, does not count); Data when there is at least one table; Preview when the app was shown running at the saved revision; Build when an installer exists for the saved revision. Preview and Build are remembered per app in browser storage (`lib/progress.ts`, `lsKey('studio.progress.<id>')`), never in the spec. `nextStepOf` marks one step as "(next)" with a ring: Prompt while a design waits (when you are not on it), else the first step after the current one that is not done.
- **Save on move.** Moving to another step saves first. Every way of moving goes through `go()` in the shell: the rail links, Back, Next, Use this, the in-body buttons such as "Add a form in Design", and any link on the screen (a capture phase click listener catches the Apps link and the kit sidebar while there is something to save). It saves the dirty drafts in the order Design, then Data, then navigates. Each of Design and Data registers a draft with `setDraft(tab, { save, saveBlocked, nextBlocked })`. If the save is refused or `saveBlocked` is set, the stuck dialog opens: "Your changes on Design cannot be saved yet", the reason, **Discard changes** or **Stay** (focus starts on Stay). The page picker and Page actions in Design follow the same rule, with their own dialog. `beforeunload` guards a reload while there is unsaved work. The browser Back and Forward buttons go through the same gate: while there is unsaved work or the helper is active, the workspace keeps one extra history entry on top (a sentinel at the same address) and a `popstate` is answered by the same `go()` path, so the same dialogs ask. Unsaved Data and Design edits are also kept in browser storage per app and step (`lib/draftStore.ts`, `hooks/useDraftStore.ts`); opening the step again offers them back in the notice line with **Restore** or **Discard**, never applying them silently. The prompt words are kept per app too (`lib/appMemory.ts`). Leaving the app while the helper runs or its design waits asks first ("Stop the helper and leave?" or "Leave without using the helper's design?", **Stay** is the way back).
- **Save, and Save in the card.** **Save** (Design toolbar, Data card) and Ctrl+S save without moving. The header holds the one save status, plain text and not a live region; a finished save is announced once ("All changes saved.").
- **Back and Next live only in the rail**, at its right end, in the same place on every step: `Back: <Step>` and `Next: <Step>` (`backLabel`, `nextLabel`), none before Prompt and none after Build. The busy word is "Saving...". **One primary button per screen.** Next is the primary button only on Design, Data and Preview, whose bodies have none. On Prompt and Build the body has the primary (**Make my app**, or **Use this** while a design waits, and **Make installer**) and Next is a secondary button. Next is disabled with a visible reason (`aria-describedby`) when: a design waits on Prompt ("Press Use this or Try again first."), Design has a part that needs a table (a write part kept on purpose with "Keep it this way" does not block Next), or Data has a table that needs a fix.
- **Focus and announcement on a step change.** Every move to a step carries `STEP_FOCUS` in the router state. The shell then focuses the step heading (`h3`, `tabIndex={-1}`) and announces "<Step>, step n of 5." in the one polite announcer (`LiveAnnouncer`), after any save line of the same moment. `document.title` reads "<Step>, <App name>, Local App Studio" (`useDocumentTitle`); Apps, Features and the Feature builder have their own titles. When the helper's design arrives while you are on Prompt, Studio does not move: the review pane on the same screen takes focus on its heading and the announcer says "The helper made a design. Check it, then press Use this." (plus a sentence when it removes data); on another step it announces "The helper's design is ready. Open Prompt to check it."
- **Help.** The **Help** button in the app header and on Apps and Features, and the ? key (not while typing in a box and not with a dialog open), open one sheet: the five steps, the save rule and every shortcut (`lib/shortcuts.ts`, which `docs/USER_GUIDE.md` copies).
- **Show as.** Preview and Design show the app light unless its theme is dark. The Light or Dark "Show as" choice is a view choice kept per app in browser storage (`theme/viewMode.ts`), never in the spec. No stored choice reads as the theme's own mode (`defaultMode`), else light. Studio's own chrome keeps following the computer.
- **StudioConfirm and Undo.** A change inside an unsaved draft (a field, a table, a part, a width) is taken back with **Undo**, never confirmed: Data keeps its own history (`lib/draftHistory.ts`), Design keeps one (`useLayoutEditor`). Only an action that changes stored data at once asks first, through `StudioConfirm`: Delete app, Delete the page, Delete feature, Reset preview data, Stop build, a Data save that removes preview data ("Save and remove data?"), Discard changes that cannot be saved, and leaving with the helper's design. The shape is always the same: a title "Verb thing?", one line of consequence, a confirm button "Verb thing", a cancel button "Keep thing" (or "Stay"), and a busy word "Verbing...". It is a `role="alertdialog"`, focus starts on the cancel button, it cannot be dismissed while busy, and a failure shows its message, or "That did not work. Nothing was changed. Try again.", inside the dialog.

## Studio glossary

One name per thing, in this order of use. Use these words in every Studio string.

| Word | Means | Not |
| --- | --- | --- |
| step | Prompt, Design, Data, Preview or Build | stage, tab, phase |
| prompt | the words the person gives the helper on the Prompt step ("Your prompt") | description, instruction, query |
| page | one screen of an app | view, route |
| part | a built-in piece on a page (Heading, Table of records, Form) | block, tile, layer, component |
| feature | a saved group of parts; "your features" for the person's own | template, snippet |
| menu bar | the bar of buttons and links on every page | nav, navbar |
| table, field, record | what the app keeps; one piece of it; one row of it | schema, column, row (in Data and Preview copy) |
| preview data | the records added while trying the app in Preview | scratch data, test data, database |
| the helper | Ollama on this computer ("the helper (Ollama)" once per card) | Assistant, the model, the AI |
| installer | the Windows file Build makes | build, package, exe |
| app file, feature file | an exported app, an exported feature | spec, AppSpec, JSON |
| slot | a place in a feature that is filled in when the feature is added to an app; builder only (the Feature builder says "Add a table slot", "Add a field slot", "Uses slot <Label>" and "Slots") | anywhere else: in an app, Design, Data and the Features page say "setting" or "table" |

Never shown to the person (on every screen except the Feature builder, where "slot" is allowed): spec, AppSpec, layer, source, mode, block, tile, slot, schema, JSON, id, route, revision, toolchain, prop, bind, and part type names such as DataTable or QuickAdd. Every refusal and problem sentence shown in Design goes through `plainMessage` (`src/studio/lib/issueWords.ts`), so the menu bar refusal reads "The menu bar takes buttons, links, search boxes, quick adds, text and rows." and the messages that point to Data say "the Data step". The proof flows scan each screen for the never-shown words (the Feature builder's scan leaves out slot).

In an error, `error` is the sentence and `code` is the machine code. The sentence is for the person, the code is for tests, logs and the translator (`errorWords`); a screen shows the sentence and the action, never the code, except in Copy details and the Diagnostics log, which are made to be shared. Old bodies that carried the code in `error` still read correctly (the translator takes `code ?? error`), and `message` is a deprecated alias of `error`. See "Error codes" above.

Shelf categories: Layout, Navigation, Records, Input, Actions, Your features (`CATEGORY_LABELS` in `showcase/entries.ts`).

## Checklist for a UI change

1. Tokens and shared components only. No new color, no new button style.
2. Light and dark both look right and pass 4.5:1 for text.
3. Keyboard: reachable, visible focus, Escape closes dialogs, names on icon buttons.
4. Empty, loading and error states exist and follow the patterns above.
5. Copy follows the rules above.
6. The contrast test is green, any accessibility checks pass, and screenshots (light and dark, demo data only) are described in the PR. The steps are in `.claude/commands/ship-feature.md`.
